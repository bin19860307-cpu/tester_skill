# 数据敏感度闸门与工具路由 SOP

> 版本 v1.0 ｜ 来源：微信文章《测试用例别让 AI 硬补：先排 7 类风险》+ 支付/权限类系统的实践沉淀
> 用途：Phase 5.5 生成接口用例代码前必须先过这道闸门。

## 一、核心原则

AI 可以帮你把测试意图翻译成测试代码，但它**不能替你决定风险优先级**，也**不能碰敏感数据**。

- 测试的目标不是覆盖率好看，而是风险真的下降。
- 能上传文件，和你是否有权上传这份文件，是两件事。

## 二、8 类输入材料（先收齐再让 AI 排风险）

1. 需求或任务说明
2. 本次代码 diff 或变更摘要
3. 目标函数/接口/页面/业务流程
4. 现有测试文件和命名规范
5. 最近出现过的 bug / 线上故障 / 用户反馈
6. 输入输出约束、权限规则、状态流转、边界值
7. 项目测试框架、运行命令、mock 方式、CI 要求
8. **不能上传 / 暴露 / 让 AI 猜的内容**（见第四节）

> 最容易漏的是第 5 项（历史 bug）和第 8 项（隐私）。测试最该覆盖的地方，往往是历史上出过问题、业务上最贵、用户最容易撞到的地方。

## 三、工具路由四选一（按代码/数据敏感度）

| 路线 | 适用 | 优点 | 风险 / 限制 |
|------|------|------|-------------|
| **A. IDE 内代码助手** | 日常补测试 | 上下文近、能直接跑 | 确认账号授权与数据外发规则 |
| **B. 普通对话 + 小片段**（脱敏后） | 轻量分析 | 可控、易脱敏 | AI 不知全貌，代码仅当草稿 |
| **C. 上传脱敏文件** | 已脱敏 PRD / bug 列表 / 公开文档 | 信息量大 | 先问「离开公司环境是否仍合规」 |
| **D. 只生成空模板**（清单/矩阵/检查项） | 代码敏感 | 真实代码留本地 | 不炫但稳 |

**决策**：代码/数据敏感 → 优先 D / B；已脱敏且合规 → A / C。
**灵魂一问**：「这份文件离开公司环境，是否仍然合规？」答案不确定，就不要用 C，退回 B / D。

## 四、绝对不能上传的内容

- 生产密钥、token、cookie、数据库连接串
- 真实用户数据、客户名、手机号、邮箱、订单号
- 合同、内部漏洞、未公开路线图、生产日志

**脱敏规则（必须做）**：

- 用户 ID → `user_a` / `user_b`
- 手机号 → `13800000000`
- 订单号 → `order_001`
- 密钥 / token / cookie → 全部删除
- 真实域名 / 客户名 / 内部路径 → 只保留必要结构

## 五、适用边界（本 SOP 不覆盖）

- 医疗 / 金融 / 法律 / 车控 / 安全生产等高风险系统的**最终测试判断**
- 需合规审计、渗透测试、安全认证、监管签字的测试
- 含前述敏感原始材料的场景（除非已脱敏且合规）

## 六、与流水线的衔接

- **Phase 2.5（七类风险地图）**：缺资料必须显式标注，不许 AI 编造业务规则或历史 bug。
- **Phase 5.5（接口用例代码生成）**：生成前先过本闸门；运行中按「失败日志三分法」迭代（测试写错→修测试 / 环境缺失→补环境 / 业务 bug→让测试失败提 bug）。
- **对抗性评审模板（六）**：含「是否含密钥 / 真实客户数据 / 生产日志」必查项。
