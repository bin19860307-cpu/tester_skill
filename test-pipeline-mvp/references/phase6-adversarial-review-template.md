# 对抗性评审模板（六）— 交叉复核

> Phase 5.5（接口代码执行）与 Phase 6（用例评审）共用的复核模板。
> 定位：**红线卡下限，复核提上限**。机械规则负责判对错，本模板负责把人对自己的结论再挑一遍刺。

---

## 一、失败日志三分法（Phase 5.5.2）

接口用例跑完后，失败日志不许「看一眼就改测试」。必须逐条落到下表三类之一，并给出判定依据。

| 分类 | 判断依据 | 处理方式 | 禁止动作 |
|------|----------|----------|----------|
| **测试写错** | 断言过严/过松、测试数据不合规、fixture 或 mock 未就绪、调用顺序与真实链路不符 | 修测试后重跑 | — |
| **环境缺失** | 依赖服务未启动、库表未初始化、账号/权限未准备、mock 与真实契约不一致 | 补环境后重跑，登记补救动作 | 把环境问题记成「业务 bug」 |
| **业务 bug** | 复现稳定、断言符合需求契约、换数据仍失败 | **保留失败**，提缺陷单，记录缺陷编号 | **不得**删断言、改业务逻辑、放宽预期来「通过」 |

判定顺序（不可颠倒）：

```
1. 换一组合法数据重跑 —— 仍失败？ 否 → 测试数据问题（归入测试写错）
2. 手工/接口工具直连同一接口 —— 表现一致？ 否 → 测试代码或环境问题
3. 对照需求契约（字段、状态码、副作用） —— 断言与契约一致？ 否 → 断言写错
4. 以上都排除 → 业务 bug，保留失败并提缺陷
```

常见反模式（出现即判定为「测试写错」，不得计入业务 bug）：

- 断言只查「返回 200 / 方法被调用」，不查数据与副作用
- 用生产数据结构硬编码，换环境即失败
- mock 返回体与真实契约字段名不一致
- 为让用例通过而 `assert True` / 注释断言 / 放宽阈值

## 二、换角色挑刺（Phase 6 人工评审前）

同一份用例集，用三个视角各扫一遍，每个视角至少产出一条意见（**"没有意见"不算通过，要写明扫过哪些维度**）：

| 视角 | 关注点 | 典型问题 |
|------|--------|----------|
| **执行人**（不懂实现） | 步骤能不能照做？预期能不能判？ | 缺导航路径、预期写「功能正常」、依赖设计稿 |
| **开发**（知道实现） | 用例是否绕过了真实风险？ | 只测 happy path、边界值缺失、并发/幂等没覆盖 |
| **攻击者**（恶意输入） | 信任边界在哪？ | 越权访问、参数篡改、级联失效、隐式约束未验证 |

产出格式：

```markdown
## 三角色挑刺记录
- 执行人：<发现的问题，或「已核对 步骤可执行性/预期可判定性/数据齐备性，无问题」>
- 开发：  <...>
- 攻击者：<...>
```

## 三、模板核对清单（8 项，逐项打勾）

- [ ] 1. 每条用例可回溯到需求点 / 规则 / 风险（无孤立用例）
- [ ] 2. 步骤含导航路径，执行人无需询问即可操作
- [ ] 3. 预期具体到可判定（文案、状态、数据），无「正常」「成功」这类空话
- [ ] 4. 步骤与预期编号 1:1，纯导航步骤标 `-`
- [ ] 5. 正向 / 反向 / 异常三类齐备，异常场景真实可能存在（非编造）
- [ ] 6. 权限与角色维度按矩阵覆盖，含豁免场景
- [ ] 7. TP-A 攻击性用例覆盖 信任边界 / 隐式约束 / 级联失效 三大盲区
- [ ] 8. 无「合并验证」「已由主用例」等内部标注污染步骤与预期

任一项未过 → 回到对应阶段修正；**不得豁免进入 Phase 7**。

## 四、上下文占用警戒线

长任务跑到 Phase 5 之后，上下文容易过载，表现为：用例开始「套模板重复」、忘记前面确认过的规则、追溯字段丢失。

处置：上下文占用 **≥ 40%** 时主动做一次交接（写 `references/pipeline-state-template.md` 状态文件 → 重开会话 → 从状态文件恢复），而不是硬撑。硬撑的代价是静默降质，比中断更贵。
