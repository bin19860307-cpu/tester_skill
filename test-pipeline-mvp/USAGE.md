# 使用说明 — test-pipeline-mvp 详细使用路径

> 本文是**从安装到出交付物**的完整操作路径。`SKILL.md` 是执行规则基线（Agent 读），本文是给人看的使用手册。
> 跟着「第 1 → 第 6 节」走一遍，大约 15 分钟能跑完一个完整案例。

---

## 1. 安装

### 方式一：命令行（推荐，支持 Claude Code / Codex / Cursor / Gemini CLI 等）

```bash
npx skills add bin19860307-cpu/tester_skill --skill test-pipeline-mvp
```

### 方式二：手动复制目录

把整个 `test-pipeline-mvp/` 目录复制到对应客户端的 skills 目录：

| 客户端 | 目录 |
|---|---|
| WorkBuddy | `~/.workbuddy/skills/` |
| Claude Code | `~/.claude/skills/` |
| Codex | `~/.codex/skills/` |

### 方式三：WorkBuddy 技能市场

在 WorkBuddy 技能市场搜索「测试工程全流程流水线」安装（上架后可用）。

### 安装后自检

在对话里输入触发词，看 Agent 是否加载本技能：

```text
跑一下测试流水线
```

正常表现：Agent 进入 **Phase 0 测试范围确认**，先问你需求范围，而不是直接吐用例。
如果没有任何反应，检查目录下 `SKILL.md` 是否存在、文件名是否被改过。

## 2. 五分钟跑通第一个案例

用一句话需求走完整流程。**每一步 Agent 都会停下来等你确认**（这是设计，不是卡住）。

### 步骤 1：给需求

```text
用测试流水线分析这个需求：管理员可以创建用户，填写姓名、手机号、所属部门，保存后出现在用户列表
```

### 步骤 2：确认测试范围（Phase 0）

Agent 会拆成三个区域让你确认：

| 区域 | 含义 | 你要做的 |
|---|---|---|
| Zone 1 核心 | 本次必须覆盖的主流程 | 确认无遗漏 |
| Zone 2 交互 | 跨模块联动点 | 确认是否需要覆盖 |
| Zone 3 排除 | 本次不测的范围 | 确认排除理由成立 |

### 步骤 3：补全需求（Phase 1）

Agent 会列出**缺失信息**（字段校验规则、权限、异常提示文案等）并追问。
**别跳过**——这一步偷懒，后面用例的预置条件和预期就会变虚（这是 AI 首跑最常见的瑕疵）。

### 步骤 4：逐阶段确认

后面每个阶段都会输出产物并等你确认：

- Phase 1.5 流程图 → 确认业务流程节点对不对
- Phase 2 需求拆解 → 确认用户故事与模块交互矩阵
- Phase 3 测试点 → 确认七维度覆盖与分组
- Phase 3.5 覆盖率 → 看节点覆盖率与缺口
- Phase 4 测试点评审 → 确认优先级与取舍
- Phase 5 用例生成 → 确认用例结构与内容
- Phase 6 用例评审 → 看自动评审 + 三层交叉验证结论
- Phase 7 用例修改 → 确认逐条修订
- Phase 8 交付确认 → 拿到最终产物清单

### 步骤 5：导出

```text
导出 Excel
```

得到标准用例表（默认 12 列结构；与 `excel-testcase-18col` 配合可出 18 列企业模板）。

## 3. 全流程阶段一览

| 阶段 | 做什么 | 主要产物 | 人工卡点 |
|---|---|---|---|
| **Phase 0** | 测试范围确认（三区域划分） | 范围清单 | ✅ 必须确认 |
| **Phase 1** | 需求分析 & 补全、模块边界、规则建模 | 需求分析稿 | ✅ 必须确认 |
| **Phase 1.5** | 流程图绘制 | Mermaid 流程图 + 节点清单 | ✅ 必须确认 |
| **Phase 2** | 需求拆解 | 用户故事 + 模块交互矩阵 | ✅ 必须确认 |
| **Phase 3** | 测试点生成（七维度 + 跨模块交互 + 路径绑定） | 测试点清单（主功能点分组） | ✅ 必须确认 |
| **Phase 3.5** | 覆盖率验证 | 节点覆盖率 + 缺口清单 | ✅ 确认 / 补充 |
| **Phase 4** | 测试点评审 | 覆盖度检查 + 优先级打分 | ✅ 确认 / 修改 |
| **Phase 5** | 测试用例生成 | 用例表（12 列结构） | ✅ 必须确认 |
| **Phase 6** | 测试用例评审 | 自动评审 + 三层交叉验证结论 | ✅ 确认 / 修改 |
| **Phase 7** | 测试用例修改 | 逐条修订后的用例 | ✅ 必须确认 |
| **Phase 8** | 交付确认 & 导出 | Excel + 产物清单 | ✅ 必须确认 |
| Phase 8.5 | Obsidian 同步（可选） | 按版本组织的知识库副本 | 仅正式版，`--no-sync` 可跳过 |

**卡点规则**：标注 ✅ 的阶段会停下来等你回复，不会自动往下跑。想快可以连续回复「确认」，但不建议在 Phase 1 / Phase 3 省这一步。

## 4. 典型使用场景

### 场景 A：一句话需求 → 完整用例（最常用）

```text
用测试流水线分析：用户可以修改密码，需要旧密码验证，新密码 8-20 位且含大小写字母和数字
```

### 场景 B：有需求文档（PDF / Word / Markdown）

```text
@需求文档_v1.2.pdf 跑一下测试流水线，最后导出 Excel
```

支持 PDF（含截图内容提取）、Word、Markdown。图片类需求会走视觉内容识别。

### 场景 C：需求变更 → 增量补充（不重跑全流程）

```text
需求变了：姓名改为必填且限 2-20 字，手机号改为唯一。
基于已有测试点做增量补充，不重跑全流程，只补受影响的部分
```

适合版本迭代后期。Agent 会定位受影响的测试点与用例，做增量修订并标注变更来源。

### 场景 D：覆盖率查漏补缺

```text
基于现有测试点做 Phase 3.5 覆盖率分析，找出没覆盖到的流程节点和分支
```

### 场景 E：已有用例做质量评审

```text
@现有用例.xlsx 用测试用例评审阶段（Phase 6）过一遍，按 17 条质量规则打分并列出问题
```

### 场景 F：与 18 列企业模板配合

```text
用测试流水线生成用例，然后按 excel-testcase-18col 的 18 列标准导出
```

## 5. 评测体系：给你的用例质量打分（可选但强烈建议）

流水线跑出的用例到底好不好？靠感觉不准。本技能内置一套量化评测，用「三率」说话。

### 5.1 原理

选一条**稳定的核心正向需求**做基准，同一版本跑两次：

- **首跑**：AI 直接生成的用例（`first-run.xlsx`）
- **封版**：测试人员评审修改后确认的用例（`final.xlsx`）

对比两版，算出：

| 指标 | 含义 | 说明 |
|---|---|---|
| 留存率 | 首跑用例未被改、未被删的比例 | ≈ 有效率，含漏检风险，不等价于"质量好" |
| 修改率 | 被封版改动的比例 | 细分轻改 / 重改（内容差异阈值默认 0.5） |
| 删除率 | 被封版删除的比例 | 反映冗余 / 幻觉用例 |
| 缺口率 | 封版新增 / 封版总数 | AI 漏生成的覆盖盲区 |

### 5.2 用自带示例数据立即试跑

仓库自带一组**通用示例数据**（虚构的「用户管理」模块），装完就能验证脚本能不能跑：

```bash
cd test-pipeline-mvp

python scripts/eval_metrics.py \
  --first baseline/demo/first-run.xlsx \
  --final baseline/demo/final.xlsx
```

预期输出：

```text
首跑用例总数 N      : 8
留存(首跑采纳率)    2  | 留存率   : 25.0%
修改           5  | 修改率   : 62.5%
  ├ 轻改(小修)    2  | 重改(大改)    3  (阈值 0.5)
删除           1  | 删除率   : 12.5%
封版新增(缺口)    1  | 缺口率   : 12.5%
```

> 依赖：`pip install openpyxl`（仅评测脚本需要，纯对话使用不需要任何依赖）

### 5.3 建立你自己的基线（4 步）

1. **建基准集**：在 `eval/` 下放 `req-001-<模块>-<核心正向流程>.md`，只写需求描述（背景、角色、前置、主流程、预期），**不要放用例**
2. **跑两版**：流水线跑出首跑 → 人工评审封版 → 两个 xlsx 都留好（建议放 `eval/runs/run-YYYYMMDD-<模块>/`）
3. **算三率**：

   ```bash
   python scripts/eval_metrics.py \
     --first eval/runs/run-20260101-用户管理/first-run.xlsx \
     --final eval/runs/run-20260101-用户管理/final.xlsx \
     --out baseline/eval-result.json
   ```

4. **冻结基线 + 记一笔**：
   - `baseline/skill-version.json` 填 Skill 版本 + 文件清单
   - `baseline/model-version.json` 填模型 / Agent 与版本（**换模型后三率不可直接对比**）
   - `CHANGELOG.md` 追加一条「改动-效果对照」：改了什么 → 三率如何变化 → 结论

> **冻结条件**：封版用例不再变动 + 测试人员最终确认后，才冻结。冻结前算的三率没有归因意义。

### 5.4 让三率有意义的三条纪律

1. **同模型对比**：换了模型或大版本，重新建基线，不要跨模型比三率
2. **同口径**：首跑定义、评审标准、分母口径保持一致，否则数字不可比
3. **单变量**：一次只改一处规则（一条规则 / 一段提示词），改完全量重跑，才能判断是这条改动起了作用

## 6. 参数与适配

评测脚本支持不同模板与命名规范：

| 参数 | 用途 | 默认 |
|---|---|---|
| `--name-cols` | 用例名称列候选（逗号分隔） | `用例名称,用例编号,名称` |
| `--content-cols` | 判定「是否被修改」的内容列 | `预置条件,测试过程,接收标准,优先级,用例类型,用例性质,状态,类型,可测试,基础用例` |
| `--group-col` | 按某列分组统计（如 `测试套件`） | 不分组 |
| `--entity-col` / `--entity-val` | 只统计实体标识为「测试用例」的行（排除套件行） | 不过滤 |
| `--name-strip` | 名称正则剥离，处理命名规范差异，如 `"【[^】]*】"` | 不剥离 |
| `--no-fuzzy` | 关闭模糊匹配（名字对不上的首跑用例直接判删除） | 开启（阈值 0.55） |
| `--heavy-threshold` | 轻改 / 重改的分界阈值 | 0.5 |
| `--out` | 结果写入 json 路径 | 只打印不写文件 |

常见适配：

```bash
# 18 列企业模板，只统计「测试用例」实体行，按测试套件分组
python scripts/eval_metrics.py --first a.xlsx --final b.xlsx \
  --entity-col 实体标识 --entity-val 测试用例 --group-col 测试套件

# 封版用例统一加了【非基础用例】前缀，比对前剥离
python scripts/eval_metrics.py --first a.xlsx --final b.xlsx --name-strip "【[^】]*】"
```

## 7. 常见问题

**Q：Agent 没有进入 Phase 0，直接开始写用例？**
A：技能没被加载。确认 `SKILL.md` 在 skills 目录第一层（不是嵌套在子目录），再重试触发词。

**Q：每个阶段都停下来等我，太慢？**
A：这是人工卡点设计。**不要跳过 Phase 1（需求补全）和 Phase 3（测试点）**——这两步省了，后面用例的预置条件和预期必然发虚，返工成本更高。

**Q：需求不全，能直接生成吗？**
A：会生成，但 Agent 会先追问缺失信息。需求文档缺失关键规则时，明确说"按你的假设生成并标注假设"，它会把假设列出来供你核对。

**Q：跑 `eval_metrics.py` 报 `ModuleNotFoundError: openpyxl`？**
A：`pip install openpyxl`。只用流水线对话不需要它。

**Q：三率算出来留存很低，是 Skill 不行吗？**
A：先排除口径问题——封版是否真的逐条评审过、是否换了模型、首跑是否被人工干预过。留存率低通常指向两个具体缺陷：预置条件过简、预期不可验证。这两个正是 Phase 1 补全和 Phase 5 生成的重点。

**Q：能只跑其中某个阶段吗？**
A：可以。直接说"只做 Phase 6 评审"或"基于现有测试点做 Phase 3.5 覆盖率分析"，Agent 会跳过前置阶段。
